# Tastes — Workflow & Tooling
- Prefers an orchestrator-style multi-agent workflow: the main agent should break tasks into small, self-contained chunks, delegate each to a sub-agent (Explore for research, Plan for design decisions, General for implementation), run independent chunks in parallel, and review/assemble the results itself rather than doing large tasks end-to-end. User explicitly requests this for research AND for implementation ("spin up different agents and do the research and create a list"; "spin different agents for this?" — repeated for each new research track, e.g. components then design directions; "plan according, spin different agents and do this" when turning the approved wireframe into the real site; "nwo spin different agents" for animation research across categories). Confidence: 0.99
- Prefers deploying finished sites to Vercel for hosting ("host the website on vercel"). Confidence: 0.6
- Prefers documenting agent workflows and roles in AGENTS.md files — a global file (e.g. ~/.commandcode/AGENTS.md) plus per-project files — rather than keeping that knowledge only in conversation. Confidence: 0.9
- Relies on persisted plan files (e.g. ~/.commandcode/plans/) for cross-session continuity: expects the assistant to check prior sessions' plans, git history, and current project state before answering status questions or continuing work. Confidence: 0.6
- When the user says to continue/resume a task ("check what task we were doing in this repo and go ahead with the task"; "check the older session what had done in this case and go ahead with the implementation"), expects the assistant to reconstruct the in-flight task itself from repository state — saved session/context files, git status/log, untracked artifacts (wireframes, screenshots), and taste-file diffs — and proceed autonomously to completion, rather than asking the user to restate the task. Confidence: 0.85
- Prefers wireframe-first UI development: produce editable wireframes for the owner to review and approve before anything is built or polished — including explicit plan-then-wireframe-first sequencing before redesign work ("plan it properly and create the wireframe first"). Confidence: 0.95
- When the user declares the current design inadequate ("our website wireframe now is very simple and like ai made it"), expects a complete redesign cycle rather than incremental tweaks: research the best/world-class reference sites ("search for best portfolio in world") + consult the curated component sources ("use our resources if required"), plan properly first, then create a NEW versioned wireframe with lots of interesting transitions for approval — before touching the real site. Confidence: 0.7
- Prefers non-destructive, versioned iteration on artifacts: when moving to a new design direction, build the new wireframe as a separate file (e.g., v2) with a link back to the old one rather than overwriting — "create the new wire … without disturbing the old wireframe" — so prior versions stay intact and comparable. Confidence: 0.9
- Wants the wireframe itself to be self-editable by the owner — click-to-edit in the browser with autosave, plus an export (JSON/HTML) the assistant can port back into the real site — so the owner iterates on the design directly instead of round-tripping every change through the assistant. Confidence: 0.8
- Prefers iterative, incremental wireframe refinement: components added to the editable wireframe one at a time in priority order (based on the established ranked list and reference research), previewing the evolving "final look" in the browser before anything is ported into the real site — rather than implementing all pieces in one shot. Confidence: 0.8
- Prefers skills and tooling configuration to be enabled globally — available across all sessions, tools, and machines — managed from a single git-tracked source of truth (e.g. a config repo symlinked into `~/.agents/skills/`) rather than per-project or per-session setup, with changes committed and pushed immediately. Confidence: 0.8
- Prefers terse, imperative requests and immediate action ("do it now") over confirmation loops or lengthy back-and-forth before starting work. Confidence: 0.9
- When a task is blocked on the user (e.g., an expired OAuth/device-auth login), expects the assistant to re-trigger the flow itself and drive the task to full completion ("do it now and complete the whole task"; user green-lit the proposed `gh auth refresh` re-run with "yeah go ahead") — not leave it half-done or hand commands back for the user to run. Confidence: 0.8
- After the owner selects a batch of picks from a ranked list (referenced by number), expects them all implemented properly in one pass and the final wireframe delivered ("implement it properly and give me final wireframe") — not piecemeal additions, further preview rounds, or re-asking for confirmation. Confidence: 0.7
- Treats wireframe/plan approval as the green light for a single continuous implementation pass with no further checkpoints: once the owner says to implement ("go ahead and start implementing the above wireframe ... make the code changes and deploy it now"), expects the full port into the real codebase, build + end-to-end verification (browser QA, fidelity to the approved wireframe, data correctness, mobile/reduced-motion), and a production deploy all completed autonomously before reporting back — not a partial implementation awaiting the next approval. Confidence: 0.75

- When an external step fails (e.g., a Vercel device-code login error), expects the assistant to diagnose the root cause itself ("CHECK WHAT IS THE ISSUE") and resolve it — checking the actual state (e.g., background task output, auth status) rather than re-attempting blindly or bouncing the error back to the user. Confidence: 0.8
- Prefers using gstack for web scrolling and computer-use tooling for browser-based verification when available, rather than skipping visual checks. Confidence: 0.8
- For design/reference research, expects the assistant to actually drive a real browser — click into sites, take screenshots, and inspect the page's JS/frameworks/components — so references are evaluated technically and their techniques can be reused, not just skimmed as links. Confidence: 0.95
- For animation-focused reference analysis, expects the browsing session to be screen-recorded (a video of the live site) so motion behavior can actually be reviewed — "record the screen if required" — rather than relying on static screenshots alone. Confidence: 0.6
- When the user flags that the current wireframe is "different altogether" from a designated reference, expects a technical gap analysis of the animation/motion layer: inventory the reference's stack (e.g., GSAP, Lenis, SplitType, Swiper, CSS keyframes, scroll-linked transforms) and deliver a side-by-side comparison with concrete fixes to close the gap toward fidelity. Confidence: 0.6
- Prefers using available image-generation models (e.g., the deepseek image model) for wireframe/design visuals when such models are configured. Confidence: 0.7
- Consults the user's own provided resource lists first when conducting research (e.g., portfolio/template resources the user supplied) before falling back to general web search — the user explicitly expects provided resources to be used ("search for best animation … from sources we have provided"; "check our resources as well" when re-running research). Confidence: 0.95
- Wants to personally verify design samples and reference choices before they are adopted — deliver concrete, clickable samples for review rather than unilaterally picking and implementing references, and every referenced candidate must come with its direct, working URL ("accordingly I will [see] the site to check it"; "give me link of each so that i can refer it"). Confidence: 0.97
- When the user asks for something simple ("just give me link of portfolio you ranked better"), expects a concise, link-only reply — just the direct URLs, no repeated ranking rationale, tiers, or commentary — even if a full analysis was already delivered earlier. Confidence: 0.7
- Prefers research/verification deliverables as a browsable HTML page served via the dev server (e.g., an "inspiration board" with a ranked table plus sample links grouped by section), consistent with the editable-wireframe artifact pattern. Confidence: 0.7
- Expects finished deliverables (wireframes, sites) to be verified end-to-end — serving, headless render, no JS errors, visual screenshot check — and then opened in the browser for immediate owner review; "open the website" is part of the delivery, not an extra step. Confidence: 0.7
- Views public personal-branding surfaces beyond the website (e.g., the GitHub profile, github.com/shreyashTirpude) as fair game for AI-assisted redesign/enhancement: "so this is my github profiel … use ai make it look interesting and make it perfect" — the assistant is expected to take the user's own live profile URL and enhance it directly. Confidence: 0.5
- Functional QA pass: the user asks "test what functionality is not working," so every interactive feature (loader, nav, forms, autosave, reduced-motion) should be exercised in a real browser and reported as pass/fail, with real bugs fixed and re-verified rather than hand-waved. Confidence: 0.8
- Expects a delivered/deployed site to be QA-tested end-to-end before it's considered done: Playwright functional pass/fail on the live URL, a performance/accessibility/improvement audit, mobile compatibility at multiple viewports (no horizontal scroll, responsive grids), and public-access/shareability verification (any random person with the URL can see the site — no auth wall, Google-indexable) — the user asked for all of these in one request ("test the website using gstack skills and playwright and check what can be improved also check the test and also can we share the url any random person can see the website and is it mobile compatible"). Confidence: 0.9
- Holds a production-quality bar for deployed web deliverables: QA findings get fixed and the site is rebuilt, redeployed to production, and re-verified live — not just reported ("yeah go ahead" approving fix + redeploy). This includes no dead links (external profile handles are probed/verified to resolve before linking), a genuinely functional contact path (mailto with prefilled message rather than a fake "message ready" state), and social-share metadata + accessibility basics (OG/twitter + og:image, theme-color, canonical, focus-visible rings, ≥44px tap targets, capped boot loader). Confidence: 0.65
- When the user references an earlier instruction that isn't reflected in the current state (e.g., "i said to implement transition like this [otsuka-air.jp] ... check the history of the chats ... do search for this"), expects the assistant to search the saved record — taste-file diffs/history, plan files, git history, prior wireframe artifacts — and answer with the user's original request quoted from that record plus an honest gap analysis of what was actually built vs. what was asked, rather than defending the current implementation or answering from memory. Confidence: 0.75
